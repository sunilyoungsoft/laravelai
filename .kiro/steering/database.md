# Database Rules

## Ownership

Platform DB (`platform` connection):
Platform data only.

Workspace DB (`workspace` connection):
Company/business data (one database per company).

Never mix them.

Platform models, migrations, seeders, and services must use the `platform`
connection explicitly. Do not rely on Laravel's default connection.

Update `docs/database/platform.dbml` whenever platform_db schema changes.

## Foreign keys

Default delete behavior is `NO ACTION` (`noActionOnDelete()`).

Do not use cascade deletes unless explicitly approved.

## Soft-delete identity policy (Platform)

Unique identity fields remain reserved after soft delete. Do **not** mutate
email/phone/slug on delete, remove unique indexes, or create a replacement
row with the same identity.

- `platform_users.email` and `platform_users.phone` stay unique including soft-deleted rows.
  Restore the existing Platform User when that person needs access again.
- `platform_roles.slug` and `platform_permissions.slug` stay unique including soft-deleted rows.
  Restore the existing role/permission when the same logical identity is required again.

## Platform Admin role

The protected Admin system role (`slug=admin`, `is_system=true`) does **not**
use wildcard permissions. Whenever a future Platform feature introduces a
permission record, that permission must be assigned to the Admin system role.

`php artisan platform:create-admin` is bootstrap-only for the **first** Platform
Admin (checks include soft-deleted Admin users). Additional admins are created
later through Platform administration.

## Naming

- SQL table and column names: snake_case
- Table names: plural
- Primary keys: ULID
- Foreign keys: `{singular_table}_id`
- Boolean fields: `is_xxx`
- Timestamp fields: `*_at`

## Timestamps (UTC)

- Server timezone and application timezone: UTC
- Laravel is the source of truth for system timestamps
- Do not use MySQL `NOW()` or `CURRENT_TIMESTAMP` for application timestamps
- Do not use migration `useCurrent()` / `useCurrentOnUpdate()` for application timestamp columns unless there is a documented infrastructure reason

## Migrations

Every module owns its migrations.

Migrations must be:

- deterministic
- reversible where practical
- safe
- properly indexed

Avoid destructive migrations unless explicitly required.

## Indexes

Add indexes based on:

- foreign keys
- frequently queried columns
- unique constraints
- filtering/sorting requirements

Do not add indexes blindly.

## Relationships

Use proper database constraints where appropriate.

Prefer foreign keys for important relationships unless there is a documented reason not to.

## Transactions

Use database transactions for multi-step business operations that must succeed or fail together.

## Data Types

Choose appropriate column types.

Do not use strings for everything.

Use:

- timestamps for dates
- decimals for financial values
- ULIDs for IDs
- JSON only when structured relational storage is not appropriate

## Financial Data

Never use floating-point values for monetary amounts.

Use appropriate decimal precision.

## Workspace Database

Workspace migrations must be executable independently for every workspace.

The migration system must safely track workspace migration status.

## Tenant database identity (Stancl)

See `docs/architecture/tenancy-spike.md` for the validated details. Stable rules:

- Workspace DB name is `workspace_{lowercase_company_ulid}`. `Company` is the tenant
  entity and Company ULID is the tenant key. There is no separate Stancl `tenants` table.
- The `database_name` column is application-owned (generated by `CompanyService`).
  Stancl reads it via the Company tenant trait; it must not invent an alternate
  naming convention and must not persist its own internal keys onto `Company`.
- Creating a Company does NOT create a physical workspace database. Provisioning is a
  separate future phase; do not enable Stancl's `CreateDatabase` jobs by default.
- The `platform` connection is permanently central. While tenancy is initialized the
  default connection becomes `tenant`, so any Platform model/query must still name the
  `platform` connection explicitly rather than relying on the default.
- `companies.slug` and `companies.database_name` remain reserved after soft delete
  (same identity policy as platform users/roles/permissions above).
